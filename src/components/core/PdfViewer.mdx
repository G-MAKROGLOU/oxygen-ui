# PdfViewer

A virtualized, in-browser PDF viewer built on [pdfjs-dist](https://mozilla.github.io/pdf.js/). It renders only the pages currently inside the viewport, supports a selectable text layer with in-document search, and provides a configurable toolbar with zoom, page-jump, fit controls, download, and print.

**pdfjs-dist is loaded lazily.** It is not part of the entry bundle and only fetches on first render.

```tsx
import { PdfViewer } from '@geomak/ui'
```

---

## Source types

`PdfViewer` accepts four source shapes via the `source` prop.

<table style={tbl}>
  <thead><tr><th style={th}>Shape</th><th style={th}>When to use</th></tr></thead>
  <tbody>
    <tr><td style={td0}>string | URL</td><td style={td(false)}>Remote URL; the only mode that performs a network request.</td></tr>
    <tr><td style={td0}>File | Blob</td><td style={td(false)}>Local file from an input[type=file] or a fetch response blob.</td></tr>
    <tr><td style={td0}>ArrayBuffer | Uint8Array</td><td style={td(false)}>Programmatic bytes, e.g. generated by jsPDF or received from a WebSocket. No network.</td></tr>
  </tbody>
</table>

```tsx
// Remote URL
<PdfViewer source="https://example.com/report.pdf" />

// File from <input type="file">
<PdfViewer source={fileInputRef.current.files[0]} />

// Programmatic bytes
<PdfViewer source={uint8ArrayBytes} />
```

For remote sources, pass HTTP headers or credentials via the `remote` prop:

```tsx
<PdfViewer
  source="https://api.example.com/report.pdf"
  remote={{ httpHeaders: { Authorization: `Bearer ${token}` } }}
/>
```

## Text layer and search

When `textLayer` is `true`, invisible `<span>` elements are overlaid on each page, aligned to PDF glyphs via transform matrices from pdfjs-dist. Text is selectable and copy-pasteable.

The search bar requires `textLayer`. Search is debounced (220 ms). Every occurrence of the term is highlighted in the text layer of the rendered pages; the active occurrence has a stronger accent style. Enter steps to the next occurrence, Shift+Enter to the previous one, with wrap-around and across page boundaries. Escape closes the search bar and clears the highlights. The counter shows `n of total` occurrences and announces through a polite live region.

Matching is normalized on both sides: NFKC (ligatures such as `ﬁ` match `fi`), soft hyphens are ignored, a word hyphenated at a line end matches its unhyphenated form, curly quotes fold to ASCII, whitespace runs collapse, and case is ignored.

Two behavior corrections against earlier versions: the counter counts occurrences, not pages, and matching no longer sees a fabricated space between text items that pdf.js split mid-word.

## Controlled page and programmatic highlight

`page` makes the current page controlled: a prop change scrolls to that page, and user scrolling or pager input reports back through `onPageChange` without fighting the prop. `initialPage` keeps its uncontrolled behavior.

`highlight` highlights a phrase that came from a different extractor (for example a server-side PDF pipeline):

```tsx
<PdfViewer
  source={bytes}
  highlight={{ page: 12, phrase: 'the proposed system meets the stated criteria' }}
  onHighlightResolved={({ found }) => setMissing(!found)}
/>
```

The viewer normalizes the phrase and the page text, anchors on the first 8 words, and paints from the anchor for the phrase's normalized length, clamped to the page end. On a miss it goes to the page, paints nothing, and reports `found: false`; it never guesses. The prop highlight has its own style, can be active next to a search, and is not counted in the search counter. Setting `highlight` to `null` removes the paint without scrolling.

When `page` and `highlight` are both used, the later input wins: a highlight change performs one scroll and calls `onPageChange`, so a controlled parent stays in sync.

**Limits of phrase matching.** Reading order in tables and multi-column layouts follows the PDF content stream, not the visual layout, so a phrase that crosses columns can miss. Text that is part of an image, or drawn as vector outlines, has no text layer at all. Headers and footers can interrupt a phrase that visually continues across pages; `highlight` searches one page only.

## Headless phrase search (`@geomak/ui/pdf`)

`searchPdfPhrase` runs the exact matcher behind the `highlight` prop without React, CSS, or a DOM, for example in a Node script that measures how often a server-extracted phrase resolves. It ships from its own entry point, so importing it loads no component code.

```ts
import { searchPdfPhrase } from '@geomak/ui/pdf'
import { readFileSync } from 'node:fs'

const bytes = new Uint8Array(readFileSync('report.pdf'))
const r = await searchPdfPhrase(bytes, 12, 'the proposed system meets the criteria')
// { found: true, page: 12, matchedText: '…', start: 184, end: 223 }
```

- `source` is a pdf.js `PDFDocumentProxy` (any build) or the PDF bytes. Bytes are parsed with the installed `pdfjs-dist` legacy build, which runs in Node 20+ without a DOM; a document created from bytes is destroyed before returning, a passed-in document is left alone.
- `page` is 1-based. On a miss the result is `{ found: false, page }` with no offsets.
- Options: `occurrence` picks the n-th anchor match on the page (default 0). `pageTolerance` (default 0) also searches that many pages before and after, nearest first, and reports the page where the phrase was found.
- The extraction and normalization are the same functions PdfViewer uses (`indexFromTextContent`, `findPhrase`), so for the same page and phrase `found` equals what `onHighlightResolved` reports. The lower-level matcher (`buildPageIndex`, `normalizeForSearch`, `findOccurrences`, `findPhrase`) is re-exported from the same entry.
- The page-break limit applies here too: a phrase split across two pages is found on neither, with or without `pageTolerance`.

## Virtualization

Only pages whose bounding box overlaps the visible viewport are rendered to canvas. Off-screen pages are represented by empty placeholder `<div>` elements that match the page's pixel height, keeping the scrollbar accurate.

The `overscan` prop (default `2`) controls how many extra pages are rendered above and below the viewport. Increase it to reduce blank flash on fast scrolls; decrease it to reduce memory use.

## Worker configuration

pdfjs-dist uses a Web Worker for off-thread decoding. By default the viewer injects a version-pinned CDN URL. For air-gapped environments or strict CSPs, bundle the worker and point to it:

```tsx
import workerUrl from 'pdfjs-dist/build/pdf.worker.min.mjs?url' // Vite

<PdfViewer source={bytes} workerSrc={workerUrl} />
```

## Recipes

### File from a picker

```tsx
const [file, setFile] = useState<File | null>(null)

<input type="file" accept=".pdf" onChange={e => setFile(e.target.files?.[0] ?? null)} />
{file && <PdfViewer source={file} />}
```

### Authenticated API fetch

```tsx
const [bytes, setBytes] = useState<Uint8Array | null>(null)

useEffect(() => {
  fetch('/api/report.pdf', { headers: { Authorization: `Bearer ${token}` } })
    .then(r => r.arrayBuffer())
    .then(buf => setBytes(new Uint8Array(buf)))
}, [])

{bytes && <PdfViewer source={bytes} />}
```

### Embed without chrome

```tsx
<PdfViewer source={bytes} toolbar={false} textLayer={false} height={480} width={340} />
```

### Start on a specific page at a specific zoom

```tsx
<PdfViewer source={bytes} initialPage={5} zoom={1.5} />
```

---

## Caveats

- **SSR:** pdfjs-dist is imported inside a `useEffect`, so server-side rendering is safe. Hydration renders a skeleton.
- **CSP:** The default CDN worker URL requires `cdnjs.cloudflare.com` in your `worker-src` directive. Supply a bundled worker via `workerSrc` to avoid this.
- **Large PDFs:** For documents with hundreds of pages, set `textLayer={false}` until the user requests search. The text layer multiplies DOM node count significantly.
